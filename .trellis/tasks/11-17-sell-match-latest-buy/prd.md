# 卖出配对默认最近买入并优化批次展示

## 目标

卖出配对工作台默认优先配对最近买入的可用持仓，让用户通过买入时间、成交价格和数量核对本次卖出来源。

## 背景与现状

- 用户已同意创建 Trellis 任务，最终方案确认后进入实现。
- `frontend/src/components/SellMatchDrawer.vue:12` 未传配对策略；`:16` 的按钮标注 FIFO，表格只有批次编号、配对股数和分摊成本。
- `backend/app/api/v1/router.py:298` 的预览和 `backend/app/services/ledger.py:246` 的正式记账在未提供明确配对时均使用 FIFO。
- `frontend/src/api/types.ts:56` 的批次 DTO 只有含费单位成本 `unitCost`；原始成交价来源是买入交易的 `Trade.price`，不能以单位成本替代。

## 需求

- R1：工作台默认按买入时间从近到远配对，最近一笔不足时继续使用上一笔；记账使用已预览的同一组批次和数量。
- R2：结果按实际配对顺序展示，主要信息是买入时间、原始成交价、本次配对数量；原始买入数量和可用数量以明确标签辅助展示。
- R3：批次编号使用次要短编号和完整编号提示，不占据主要表格列。
- R4：买入成交价、时间和数量来自后端真实买入数据；金额与数量继续通过十进制字符串传递，成本和收益仍由后端计算。
- R5：修改卖出数量、价格、成交时间、证券或账户后，旧预览失效；失败或过期的异步响应不能重新启用确认卖出。
- R6：旧 API 调用方未指定策略时继续使用 FIFO；工作台明确请求最近买入优先。首页和证券详情共用组件，行为保持一致。

## 验收标准

- [x] AC1（R1）：两笔不同时间买入，小额卖出优先使用较新一笔；跨笔卖出按从新到旧分配，配对总量等于卖出量。
- [x] AC2（R1、R6）：确认卖出扣减预览中的批次；旧 FIFO 和明确指定批次的手动配对继续通过回归。
- [x] AC3（R2、R3）：直接显示买入时间、原始成交价、本次配对数量；原始数量、可用数量有明确标签；长编号不挤占主要信息。
- [x] AC4（R4）：有手续费时买入价仍为原始成交价；分摊成本仍包含对应费用；时间及币种显示正确。
- [x] AC5（R1、R4）：已结清、零数量、其他账户/证券/策略和晚于卖出时点的买入不会自动配对；数量不足时有明确反馈。
- [x] AC6（R5）：输入或操作对象变化后必须重新预览；过期异步响应不能恢复旧确认状态。
- [x] AC7：前端类型检查、构建、针对配对流程的 Playwright 回归和后端匹配单测、API 集成回归通过。
